# Задание: исправления по ревью серии memory footprint

Для параллельной сессии, которая исправляет замечания. Ревью делает другая
сессия. Английские идентификаторы совпадают с кодом и комментариями на GitHub.

## Контекст

Это форк hickory-dns. В нём открыта серия PR по снижению памяти `Record`:
#1 boxing больших вариантов `RData`, #2 хранение меток `Name` в wire-формате,
#3 fast path декодера имён, #4 парсинг текста без аллокаций. Tracking issue #5.
По всем четырём PR оставлено ревью с inline-комментариями и итогами, в #5 два
сводных комментария. Дополнительно открыты PR #6 с property-тестом
`crates/proto/tests/name_props.rs` и PR #7 с новыми бенчами в
`crates/proto/benches/{name,message}.rs`. Ветка `memory-series-review-artifacts`
без PR хранит логи и таблицы ревью; `dev/memory-series-review/RESULTS.md`
содержит все числа.

Роль этой сессии: исправить замечания. Историю веток до окончания ревью не
переписывать: только добавлять коммиты и пушить в те же ветки, чтобы PR
обновлялись. Начать с чтения всех review-комментариев через GitHub MCP:
`pull_request_read` с методами `get_reviews` и `get_review_comments` для PR 1–4,
плюс комментарии в issue #5. Ниже перечислено всё существенное, но первичный
источник — сами комментарии.

## PR #2, ветка `name-wire-format`, основная работа

1. `LabelIter::next_back` сейчас идёт вперёд от текущей позиции при каждом
   вызове, обратная итерация квадратична. Сделать амортизированно O(1): при
   первом `next_back` лениво заполнить массив смещений начал меток на стеке,
   `[u8; 128]` хватает для 127 меток, дальше держать индексы front/back в этом
   массиве. Прямая итерация не должна подорожать. Критерий:
   `name_iter_rev_max_labels` не хуже main, около 210 нс, сейчас 12 500;
   `name_parse_arpa_name_ip6` не хуже main, около 360 нс, сейчас 1 050;
   `name_iter_rev_medium` без регрессии.
2. `cmp_labels` и `cmp_labels_from_root`: убрать рекурсию. Один прямой проход
   по каждому буферу в массив смещений на стеке, выравнивание по числу меток
   тем же проходом, затем сравнение пар меток от корня. Критерии по бенчам из
   #7: `name_cmp_ip6_arpa_not_eq_root` не более 25 нс, main даёт 13, сейчас
   240; `name_cmp_ip6_arpa` не хуже main, около 200 нс, сейчас 350;
   `name_cmp_long_not_eq_root` не более 12 нс, сейчас 18; `name_cmp_short`,
   `medium`, `long` без регрессии относительно текущей ветки.
3. Inline-буфер `TinyVec<[u8; 44]>` вместо 40: размер `Name` остаётся 56 байт,
   проверено на tinyvec 1.11.0.
4. Тесты на размер в 64-битных сборках: `size_of::<Name>() <= 56` и
   `size_of::<LowerName>() <= 56`, по образцу `test_rdata_is_small` из #1.
   Assert на `Record` не добавлять, он зависит от #1.
5. Unit-тесты в `name.rs` на инварианты представления: байты длины проходят
   `to_lowercase` и `eq_ignore_ascii_case` нетронутыми, включая метку из 63
   заглавных букв; `cmp` при разном числе меток; чередование `next` и
   `next_back`.
6. Обновить описание PR: назвать обе регрессии и показать до и после по бенчам
   #7.
7. Не расширять PR: оптимизация `emit` без сжатия прямым копированием буфера —

## Правила для каждого пуша

- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test -p hickory-proto --features dnssec-ring,serde`
- `HICKORY_NAME_PROPS_SCALE=10 cargo test -p hickory-proto --test name_props`
- `cargo check -p hickory-proto --no-default-features`
- для #2 и #3 бенчи на nightly до и после, два прохода, числа в комментарий к
  PR: `RUSTFLAGS="--cfg=nightly" cargo +nightly bench -p hickory-proto --bench name --bench message`

Nightly ставится так: `rustup toolchain install nightly --profile minimal` и
`rustup component add --toolchain nightly clippy`. При сравнении двух версий в
разных worktree каждому свой `CARGO_TARGET_DIR`: cargo хэширует артефакты по
пути относительно корня workspace, и общий target подменяет одну сборку другой.
Бенчи гонять на тихой машине, без параллельных сборок.

Стиль проекта: без паник и `unsafe` в библиотечном коде, stable Rust,
комментарии объясняют инварианты, сообщения коммитов на английском в формате
`proto: ...`, один смысловой шаг на коммит.

## Сдача на ревью

После пуша по каждому PR оставить один комментарий: что изменено, какие
review-треды закрыты, числа до и после. Треды не резолвить, это делает ревьюер.
Если замечание кажется неверным, написать почему в треде и не менять код. Тест
из #6 не подгонять под падение: если он падает, это находка, обсудить в PR.
Тело issue #5 не редактировать, только комментировать. В конце работы дать в
чате сводку: ветки, хэши коммитов, числа, открытые вопросы.
